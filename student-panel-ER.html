How to read the lines: a line ties two tables together. The || end means "exactly one", o{ means "many", and o| means "zero or one (optional)". So "USERS ||--o{ SAVED_VIEWS" reads as one user owns many saved views. Tables with no lines (USER_SESSIONS, SETTINGS, SCHEMA_MIGRATIONS) are plumbing — they stand alone and don't point at anything.

The new tables (5)

  • TEACHER_ASSIGNMENTS — connects a teacher (a user) to either a single student or a whole group. This is what lets a teacher see "only my students".
  • PARAMETER_ASSIGNMENTS — says which parameters apply to which group or student, instead of every parameter applying to everyone.
  • TASKS — a to-do/skill item, optionally linked to a parameter. Columns kept deliberately loose for now.
  • TASK_ASSIGNMENTS — hands a task to a group or a student (same either/or shape as parameter assignments).
  • USER_FIELD_DEFINITIONS — the mirror of student custom fields, but for user accounts (e.g. a restrictable "created on" field).

The new columns on old tables

  • students.user_id — links a student-person to their login account.
  • students.period_interval / period_anchor — that student's own rhythm (a group they're in can override it).
  • student_groups.period_interval / period_anchor — a group's optional rhythm.
  • users.extra — the values for the new user custom fields.
  • evaluations.group_id (required) and evaluations.student_id (now nullable) — every score sits under a group; a null student means it is the group's own direct score.
  • audit_log.deleted_at / delete_reason — a log line can be soft-deleted, but only with a written reason.

Two things that are independent options on a group

A group's period (its rhythm) and its parameters (what it's scored on) are separate optional settings. Any of these four is valid: a group with neither, a group with a period but no parameters, a group with parameters but no period, or a group with both. Because both are optional, they can be filled in later — nothing forces a group to have either one.

How the tree roll-up works

Groups form a tree (everything → education / performance / … → sub-groups → students). Only direct scores are stored in evaluations. A group's rolled-up number (its students plus its sub-groups, all the way down) is calculated when you look, by walking the parent_id tree — it is not saved. A group's own direct score is always shown separately from that rolled-up number.

Every table, in one line each

People & access

  • roles — named bundles of permissions (Administrator, Handler, …).
  • role_permissions — which permission keys each role holds.
  • users — login accounts; each points at one role.
  • user_field_definitions NEW — extra custom fields for user accounts.
  • user_preferences — per-user settings (theme, sort, …).
  • saved_views — a user's saved result filters.
  • user_sessions — active login sessions (plumbing).

Students, groups & the tree

  • students — the people being evaluated (now optionally linked to a login + own rhythm).
  • student_field_definitions — extra custom fields for students.
  • student_groups — the group tree (self-linked by parent_id; now with an optional rhythm).
  • student_group_members — which students are in which groups.
  • teacher_assignments NEW — ties a teacher to a student or a group.

Scoring, parameters & tasks

  • parameters — the things you measure (with min/max).
  • parameter_changes — history of parameter edits per period.
  • parameter_assignments NEW — which parameters apply to which group/student.
  • evaluations — the scores themselves; always under a group, optionally for a named student.
  • tasks NEW — to-do/skill items, optionally about a parameter.
  • task_assignments NEW — which tasks go to which group/student.

System

  • audit_log — record of every change (now soft-deletable with a reason).
  • settings — app-wide settings (plumbing).
  • schema_migrations — which DB migrations have run (plumbing).
