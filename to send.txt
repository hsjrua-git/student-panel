this we arrived at for database:
Yes, start with the database. Data is the one part that's painful to change once real students are in it. Screens and rules can be rewritten in an afternoon, but a wrong table shape means moving data. So we design the tables on paper first, and you decide what changes. Then we learn just enough (install, SQL) to build them.

So the order becomes: data model (this message) → workshop and SQL → build the tables → the rest. Stage 1, "how the web works," moves to just before the server.

The database on paper
The five words you need
Table: a list of one kind of thing, like a spreadsheet sheet (students, parameters).
Row: one item in a table (one student).
Column: one property every row has (full name).
Primary key (PK): a value that uniquely identifies a row. We use random IDs (UUIDs).
Foreign key (FK): a column holding another table's ID, pointing to a row there. The database refuses a pointer to nothing.

Two more you'll meet: a constraint is a rule the database enforces itself (required, unique, range), and an index is a lookup speed-up, like a book's index.

Design rules I followed
Store each fact once. A score refers to "Speed" by ID and doesn't repeat the word.
Calculate, don't store, what can be derived. Period dates and averages are not stored.
Never hard-delete. Rows get a deleted_at or are retired, so history stays valid.
Say who and when on things that change.
Secrets never appear in readable form (passwords are hashes only).
